# SIR-CDR 六方向 GenCDR 外部参照实验设计

## 1. 意图

在不重新训练 GenCDR 的前提下，完整运行 SIR-CDR 在三组跨域数据上的六个推荐方向：

- Sports → Clothing
- Clothing → Sports
- Phones → Electronics
- Electronics → Phones
- Book → Movie
- Movie → Book

实验尽量靠近 GenCDR 公开的时间序列留一协议，并引用 GenCDR 论文表格作为外部参照。由于作者最终人口、划分文件、候选集合和逐用户结果未公开，本实验不得被描述为严格同条件复现或统计显著击败 GenCDR。

用户已经选择：Qwen3-0.6B 完整 SIR-CDR、随机种子 42/43/44、自适应最多六张 GPU 并行；正式训练前必须先检查远程服务器条件并遵守课题组服务器规范。首次执行前由用户人工确认允许使用的 GPU，控制器只能在该白名单内调度。

执行代理不直接登录远程服务器。所有代码修改、测试和文档先在本地仓库完成，通过 Git 提交并推送到 GitHub；服务器端由用户人工执行 `git pull --ff-only` 和明确给出的命令。不得在聊天、日志或仓库中传输服务器密码、私钥或访问令牌。

## 2. 成功标准

1. 六个方向都使用冻结且可审计的数据、文本、embedding、tokenizer 和运行配置。
2. 每个方向完成三个预先声明的随机种子，报告 Recall/HR@5、Recall/HR@10、NDCG@5、NDCG@10 的均值和标准差；@20 可作为补充指标。
3. 只用验证集选择 checkpoint 和融合配置；六方向三个种子的训练、验证选参与精确验证全部完成并冻结后，才统一开放最终测试，每个种子只执行一次最终测试。
4. 任一任务中断后能从自身 checkpoint/阶段产物恢复，不覆盖或混用其他方向、种子或旧协议产物。
5. 并发度服从服务器实测资源和其他用户占用，最多六个方向同时训练，但不能抢占正在使用的 GPU，也不能以减小数据集、模型或评测目录换取速度。
6. 最终产生机器可读 JSON/CSV、逐任务日志、环境快照、数据/配置哈希、失败审计和论文可用汇总表。

## 3. 非目标和红线

- 不运行、修改或伪造 GenCDR 训练结果。
- 不把 GenCDR 论文单点结果当成相同划分下的受控基线。
- 不为了接近论文表格规模而随机抽样、替换留出样本或挑选更容易预测的用户。
- 不用测试集选择超参数、融合权重、epoch、随机种子或并发配置。
- 不对多个 SIR-CDR 种子和一个 GenCDR 论文单点进行 t 检验或显著性宣称。
- 不修改系统 CUDA、全局 Python 或其他用户环境；不占用 `/Data/public` 存放私人实验产物；不启动反向代理。
- 未经组内许可不主动占满八张 GPU。首次执行前必须由用户人工提供允许使用的 GPU 白名单；调度器上限为六卡，实际并发还必须由预检结果决定。

## 4. 已考虑的执行方式

### A. 固定六卡并行

每个方向固定一张卡，同时运行六个任务。墙钟时间最短，但会假设六张卡均空闲，也容易造成 CPU、内存、磁盘和模型缓存同时争用，不适合共享服务器。

### B. 三卡按数据对并行

每张卡负责一组数据的正反两个方向并顺序执行。资源稳定、易排查，但在六张以上 GPU 空闲时无法充分利用资源。

### C. 自适应任务队列（选定）

先完成硬件和环境预检，再从允许且空闲的 GPU 中建立可用池。每张卡同一时刻最多运行一个重型任务，最多同时运行六个方向；出现显存、主存、负载或磁盘压力时降低并发，不改变科学配置。该方式兼顾共享服务器规范、效率与结果质量。

## 5. 科学协议

### 5.1 数据协议

使用仓库已有的 `gencdr-shared-loo-v1` 隔离命名空间，并以 `experiments/run_gencdr_shared.py` 为唯一入口扩展六方向执行。核心规则保持现有实现：

- 每对域保留两域均至少五次有效交互的共同用户。
- 按时间、原始物品 ID、事件键稳定排序并保留重复交互。
- 每个目标域序列最后一次交互为测试，倒数第二次为验证，更早部分为训练。
- 源域只使用自身 `seq[:-2]`，并且时间必须严格早于当前目标标签。
- 训练采用 `all-prefixes` 展开；六个方向使用同一预先声明规则。
- 目标候选集合为完整目标目录，不采样负例。
- 屏蔽完整目标历史；重复正例命中已见集合时仍按协议屏蔽并计数。
- 文本只使用静态商品/条目字段或明确的 ID 回退，不从验证/测试评论或标签生成文本。
- 每个方向分别生成处理清单和 SHA256；正反方向不能通过简单交换已处理 JSON 字段产生。

`paper_alignment_verified` 必须保持 `false`。最终报告表注必须明确这是独立重建的近似公开协议。

### 5.2 模型与训练

- 推荐器：`Qwen/Qwen3-0.6B`，固定仓库中已声明 revision。
- 完整结构：LoRA、两步隐式推理、结构注入和 CPF；不在测试后修改结构开关。
- 默认有效 batch：microbatch 8 × gradient accumulation 2 = 16；如果实测显存不足，可降低 microbatch 并等比例增加累积步数，保持有效 batch 不变，并记录偏差。
- 最多 30 epoch，patience 5，每个 epoch 验证。
- checkpoint 选择指标：HR@10；在单正例任务中等于 Recall@10。
- 编码历史长度、候选数、融合候选和精确评测规则保持六方向一致。
- 随机种子固定为 42、43、44。seed 42 是全链路首轮；43、44 只有在相同数据和资产身份通过后启动。

### 5.3 验证与测试

每个方向和种子先训练并冻结最佳 checkpoint。预声明的融合设置只在验证集上扫描，按现有四项锚点保护与 NDCG@10 规则选择。随后执行独立精确验证，身份和指标一致后才允许最终测试。

六方向三个种子的训练、验证融合选择和精确验证全部完成后，生成一份冻结清单，包含 18 个 checkpoint、融合配置及其哈希；清单完整且一致才允许进入测试阶段。最终测试必须有不可重复预留标记；失败时保留现场并审计，不能删除锁文件后重新选择配置。测试结果输出后，不得因结果不理想改变超参数再重测同一身份。

## 6. 服务器预检与准入门槛

训练前保存带时间戳的只读环境快照，至少包含：

- `hostname`、`whoami`、当前目录和登录时间。
- `nvidia-smi` 的 GPU 型号、驱动、逐卡显存、利用率、温度、功耗和计算进程。
- `lscpu`、系统负载、内存、swap。
- 用户目录、个人 `/Data/<username>` 目录和模型缓存目录的剩余空间、inode 与权限。
- conda 环境、Python、PyTorch、CUDA runtime、`torch.cuda.is_available()`、GPU 数量和 BF16 支持。
- 仓库绝对路径、Git commit、分支、工作区状态和远端；运行身份固定到 commit，不在运行中 `git pull`。
- 原始数据、模型权重、六方向处理产物、embedding、tokenizer 和旧 checkpoint 的存在性与哈希。
- 当前用户及其他用户的 GPU 进程；不终止、不迁移、不绕过占用检查。
- 用户人工提供的 GPU 白名单；空闲但不在白名单内的 GPU 仍不可使用。

准入规则：

- 用户未给出首次运行 GPU 白名单，或白名单内没有明确可用 GPU 时，只生成状态报告，不启动训练。
- 单卡可用显存必须高于预检烟雾测试峰值并留出安全余量；具体阈值由服务器实测确定并写入运行清单。
- 磁盘空间不足以容纳模型缓存、六方向资产、18 个训练输出及安全余量时停止。
- 测试、预检、一个小规模真实 batch 前向/反向和 checkpoint 写入测试未通过时停止。
- 检测到数据、配置或代码身份变化时使用新的输出命名空间，不能覆盖已完成结果。

## 7. 分阶段并行调度

### 阶段 0：只读预检

不占用 GPU 训练。用户先人工确认 GPU 白名单，服务器命令通过 `--gpus` 显式传入；控制器再生成 `artifacts/experiment_control/.../environment_snapshot.json` 和人类可读日志，并在白名单内剔除当前忙碌或不满足准入门槛的卡。后续队列可继续使用同一白名单，但每次启动新作业前必须重新检查该卡是否仍空闲；白名单变化需要重新人工确认。

### 阶段 1：CPU 转换与审计

三个数据对可并行解析，但要避免正反方向重复读取造成 I/O 峰值。优先按数据对读取一次原始事件，再分别构建两个方向；若现有接口暂不能安全共享解析结果，则最多三路子进程，每组内部正反顺序转换。每个进程限制数值库线程，不能用六个高线程进程压满共享 CPU。

### 阶段 2：Embedding 和 tokenizer 资产

先复用相同原始条目的、身份可验证的固定 embedding；不能复用缺失模型 revision、文本哈希或域身份的旧向量。方向特定 tokenizer 独立训练并通过碰撞率、码本利用率质量门。

8B embedding 会同时消耗 GPU、CPU、RAM、磁盘和模型缓存带宽，因此不默认六路冷启动。调度器先单任务烟雾测试并测峰值，再按资源选择 1–3 路 embedding；缓存稳定后可提高。tokenizer 可在独立空闲卡并行，但仍实行一张卡一个重型进程。

### 阶段 3：seed 42 六方向推荐训练

六个方向进入任务队列；每个作业绑定一个明确的 `CUDA_VISIBLE_DEVICES`，程序内部只看到逻辑 `cuda:0`。调度器只从预检允许且持续空闲的 GPU 池取卡，最多六个并发。每个方向独立日志、PID、锁、runtime YAML、checkpoint 和 tuning 目录。

### 阶段 4：seed 43/44 复跑

只有当 seed 42 的六方向训练、验证选择和精确校验无系统错误后，才启动剩余 12 个作业。仍按方向队列调度；数据、embedding 和 tokenizer 只读共享，模型输出完全隔离。此阶段不读取或生成任何最终测试指标。

### 阶段 5：汇总

先确认 18 个作业的科学身份、最佳 checkpoint 和验证集融合选择均已冻结，再统一执行最终测试。全部测试完成后计算每个方向的均值和标准差。逐种子保留，不删除异常种子；只有明确的运行故障可以按相同身份恢复。输出六方向表、论文外部参照表和偏差说明。

## 8. 调度器行为

需要新增或扩展一个服务器端控制入口，职责仅限编排，不改变模型算法：

- `preflight`：生成环境与资产状态，返回可执行/停止原因。
- `prepare`：按阶段和资源上限准备六方向资产。
- `run-validation`：以 `(pair, seed)` 为任务单位训练、选择 checkpoint、完成验证集融合选择与精确验证，但不访问测试集。
- `freeze`：只有 18 个验证作业齐全时生成不可变测试清单。
- `run-test`：只消费冻结清单，统一执行一次最终测试。
- `status`：聚合进程、阶段、checkpoint、最近日志、GPU 绑定和失败原因。
- `summarize`：核验身份后生成 CSV/JSON。

控制器必须要求显式 `--gpus` 白名单并使用原子锁防止重复启动；重新执行时跳过已完成且身份一致的阶段，恢复中断阶段，拒绝混用身份不一致的产物。它不杀死任何已有进程，不自动抢卡，不修改系统环境，也不在后台无限轮询抢占刚释放的 GPU。

## 9. GitHub 与远程执行边界

1. 本地完成实现、单元测试、代码审阅和运行文档。
2. 所有修改形成普通 Git 提交并推送到 `bacl2166/SIR-CDR`；不把数据、模型、checkpoint、日志或凭据提交到 GitHub。
3. 每次远程实验说明固定一个 commit SHA，并提供可复制的 `git pull --ff-only`、预检、准备、验证训练、冻结、测试、状态和汇总命令。
4. 用户在服务器已登录会话中人工执行命令并在首次运行时填写确认过的 GPU 白名单。
5. 执行代理不建立 SSH 连接、不代输密码、不操作远程进程。需要诊断时，用户提供去除敏感信息的状态 JSON 或日志片段；修复仍走“本地提交 → GitHub → 服务器拉取”的路径。
6. 任何需要依据服务器实测值决定的并发参数，都由预检报告给出建议，最终启动仍由用户执行明确命令，不通过隐式远程控制改变资源。

## 10. 输出结构

所有新实验保持 `gencdr-shared-loo-v1` 隔离标识，并增加一次冻结的实验批次 ID。建议结构：

```text
artifacts/experiment_control/gencdr-shared-loo-v1/<batch-id>/
  environment_snapshot.json
  experiment_manifest.json
  scheduler_state.json
  task_status.csv

artifacts/llm_cdr_v1/gencdr-shared-loo-v1/<pair>/seed<seed>/
artifacts/tuning/gencdr-shared-loo-v1/<pair>/seed<seed>/
logs/gencdr-shared-loo-v1/<batch-id>/<pair>_seed<seed>.log
```

`experiment_manifest.json` 记录 commit、协议、六方向、种子、模型 revision、有效 batch、GPU准入策略、指标和测试政策。日志和 manifest 不写密码、令牌、SSH 私钥或其他用户的命令行敏感参数。

## 11. 结果报告

内部 SIR-CDR 表报告六方向三个种子的均值±标准差，并保留逐种子附表。GenCDR论文值放在单独的“已发表外部参照”列或表中，表注明：

> GenCDR 数值引自论文。SIR-CDR 使用独立重建的公开留一协议；由于作者最终划分、人口和逐用户预测未公开，该差值是描述性外部参照，不是严格受控的直接比较。

不对外部参照计算显著性。可以报告绝对差值和相对差值，但必须与协议偏差说明相邻呈现。

## 12. 验证与故障处理

- 修改编排代码前先为六方向注册、GPU映射、锁、失败隔离、恢复、身份拒绝和汇总编写测试。
- 本地测试不得分配生产 GPU；使用 mock 验证调度逻辑。
- 服务器先运行完整单元测试，再做单方向单 batch 烟雾测试，最后放开并行。
- 某个任务失败不会删除其他任务结果；父控制器记录退出码和最后日志。
- CUDA OOM 首先降低该任务 microbatch 并提高梯度累积，保持有效 batch；修改需形成新的运行身份或在预先允许的等效 batch 规则内记录。
- 宿主机资源压力过高时只停止启动新任务；不强杀已运行任务。必要时人工、可恢复地停止本用户任务。
- 环境或资产问题修复后用相同命令恢复；不使用 `--force` 覆盖完成产物。
